# Релиз v1.2.0: паспорт и продажа на Tolk, кошелёк, автотесты

Nov 7, 2026 · @Andrew

## Цель релиза

После релиза каждая верифицированная работа получает настоящий Digital Artwork Passport — NFT в testnet TON, который лежит в кошельке владельца и открывается в Tonviewer. Такую работу можно продать прямо в Mini App: покупатель платит в TON, контракт продажи одной транзакцией передаёт ему NFT и делит деньги между продавцом, художником и Spirit. Релиз состоит из четырёх блоков:

- **A. Первый смарт-контракт на Tolk:** реестр (NFT-коллекция) и паспорт (NFT на каждую работу).
- **B. Подключение кошелька** в Mini App через TON Connect и привязка его к пользователю.
- **C. Автотесты** на контракты и на бизнес-логику бэкенда (сейчас в репозитории тестов нет).
- **D. Продажа через контракт** с комиссиями: 12% / 8% / 80% при первичной продаже и 2% / 2% / 96% при перепродаже.

Архитектурное обоснование и схема — в документе [Smart-контракты Spirit Protocol](https://claude.ai/artifact/KMfHGX419LRtStoUUNKPvB). Этот документ — задание для разработки: что сделать, в каком порядке и как проверить.

## Принятые решения

Все решения ниже подтверждены основателем в период с 28 октября по 7 ноября 2026.

| Тема | Решение |
| --- | --- |
| Блокчейн | TON |
| Язык контрактов | Tolk — официальная документация TON называет его «the recommended language for TON smart contracts» ([Tolk overview](https://docs.ton.org/tolk/overview)); опыта с TON у команды нет |
| Сеть | Весь релиз — только testnet; mainnet после аудита |
| Vault, залог 80%, liquidity floor | Убраны из продукта 7 ноября, чтобы не отпугнуть клиентов ([PR #2](https://github.com/SpiritProtocol/spirit-protocol/pull/2)) |
| Владелец | Адрес кошелька, который держит NFT паспорта; имена людей в блокчейн не пишем |
| Кто верифицирует | Spirit и партнёры (галереи, эксперты); список verifier хранится в реестре |
| Прямая передача паспорта | Разрешена (подарок, Getgems) |
| Комиссии, первичная продажа | Spirit 12%, художник 8%, продавец 80% |
| Комиссии, перепродажа | Spirit 2%, художник 2%, продавец 96% |
| Покупатели без TON-кошелька | Нужны в будущем, но не в этом релизе |

## Скоуп

Релиз выпускает паспорта на блокчейне и продаёт работы с паспортом через контракт продажи с комиссиями. Всё работает только в testnet, деньги тестовые.

**Входит:**

- Контракты реестра и паспорта на Tolk, развёрнутые в testnet.
- Выпуск паспорта на кошелёк владельца при одобрении верификации.
- Реальная реализация `BlockchainService` за флагом `BLOCKCHAIN_MODE=real`; мок остаётся для локальной разработки и тестов.
- TON Connect в Mini App, привязка кошелька к пользователю с проверкой владения (`ton_proof`).
- В карточке работы: адрес паспорта и ссылка «Смотреть в Tonviewer».
- Контракт продажи на Tolk (один на листинг): выставление, покупка, отмена, автоматический раздел денег по комиссиям.
- Покупка в Mini App через TON Connect: покупатель платит в TON со своего привязанного кошелька.
- Автотесты контрактов и бизнес-логики бэкенда, запуск в CI.

**Не входит:**

- Оплата в USDT или в долларах, автоматический пересчёт цены по курсу.
- Vault в любом виде.
- Mainnet.
- Реальная NFC-проверка чипа: `chip_uid_hash` считается от chipId из текущего мока.
- Покупатели без кошелька, оплата картой.
- Интерфейс для партнёров-verifier (в контракте роль есть, в приложении верифицирует пока только админ Spirit).

**Правило на время релиза.** Работу с выпущенным паспортом продают только через контракт продажи; мок-покупка для неё отключена, иначе база сменила бы владельца, а NFT остался бы в старом кошельке. Демо-работы без паспорта продаются через мок, как сейчас.

## Блок A. Контракты на Tolk

Два контракта по стандарту NFT в TON (TEP-62): **реестр** — коллекция Spirit, и **паспорт** — один NFT на работу. Стандарт нужен, чтобы паспорт без доработок показывался в Tonkeeper, Tonviewer и Getgems.

### Расположение и инструменты

- Новый пакет монорепо `packages/contracts` (исходники `.tolk`, обёртки на TypeScript, тесты, скрипты деплоя).
- Инструменты выбрать на шаге 0 по актуальной документации: Blueprint + `@ton/sandbox` (по данным сообщества, поддерживает Tolk) или Acton, на который ссылается quick start официальной документации Tolk.
- Отправная точка — эталонные NFT-контракты TON, перенесённые на Tolk; не писать стандартную часть с нуля.

### Реестр (`SpiritRegistry`)

| Хранилище | Назначение |
| --- | --- |
| `authority` | Адрес администратора реестра (в testnet — сервисный кошелёк Spirit) |
| `verifiers` | Словарь адресов verifier |
| `next_item_index` | Счётчик выпущенных паспортов |
| `chip_bindings` | Словарь `chip_uid_hash → item_index`, чтобы один чип нельзя было привязать дважды |
| `collection_content`, `item_code` | Метаданные коллекции (TEP-64) и код паспорта |
| `royalty_params` | TEP-66; в этом релизе 0%, значение для внешних маркетплейсов — открытый вопрос |

| Операция | Кто вызывает | Что делает |
| --- | --- | --- |
| `mint_passport` | verifier | Выпускает паспорт на кошелёк владельца сразу со статусом APPROVED; отклоняет занятый `chip_uid_hash` |
| `set_verification` | verifier | Пересылает паспорту новый статус (APPROVED / REJECTED / REVOKED) и `evidence_hash` |
| `rebind_chip` | verifier | Перепривязка чипа (замена повреждённой метки); статус сбрасывается в PENDING |
| `update_metadata` | authority | Новая ссылка и `metadata_hash`; статус сбрасывается в PENDING |
| `add_verifier`, `remove_verifier` | authority | Управление списком Spirit и партнёров |
| `change_authority` | authority | Передача роли (потом — на мультиподпись) |

Get-методы: стандартные `get_collection_data`, `get_nft_address_by_index`, `get_nft_content`, `royalty_params`, плюс `is_verifier(address)` и `get_item_by_chip(hash)`.

### Паспорт (`ArtworkPassport`)

| Хранилище | Назначение |
| --- | --- |
| `item_index`, `collection_address`, `owner_address`, `content` | Стандарт TEP-62; `item_index` = числовая часть Spirit ID |
| `metadata_hash` | SHA-256 JSON метаданных |
| `chip_uid_hash` | SHA-256 идентификатора чипа |
| `artist_address` | Кошелёк художника; без него работу нельзя выставить через контракт продажи (см. блок D) |
| `verification_status`, `verifier_address`, `verified_at`, `evidence_hash` | Верификация; меняется только сообщением от реестра |
| `event_count`, `last_event_hash` | Цепочка событий: `hash(предыдущий хэш + событие)` |

Операции: стандартные `transfer` и `get_static_data`; служебные операции принимает только от реестра. Каждое изменение отправляет внешнее сообщение-событие. Get-методы: `get_nft_data` (стандарт) и `get_passport_data` со всеми полями таблицы.

### Метаданные

JSON по TEP-64: `name`, `description`, `image`, `attributes` (Spirit ID, художник, год, техника, размеры). Имена владельцев и любые персональные данные в JSON и в контракт не попадают. В этом релизе API отдаёт неизменяемый снимок `GET /metadata/:spiritId.json`; перенос в IPFS или TON Storage — позже, хэш в контракте от этого не меняется.

## Блок B. Кошелёк и бэкенд

Пользователь подключает TON-кошелёк в Mini App, бэкенд проверяет, что кошелёк действительно его, и выпускает на этот адрес паспорта. Бизнес-логика остаётся на бэкенде, фронтенду не доверяем.

### Mini App

- Подключить `@tonconnect/ui-react`, опубликовать `tonconnect-manifest.json` в `apps/web/public`.
- Экран Wallet (`apps/web/src/routes/WalletPage.tsx`, сейчас заглушка): кнопка подключения, адрес кошелька, сеть (testnet), отключение, список паспортов со ссылками на Tonviewer.
- Карточка работы: блок «On-chain passport» с адресом контракта и статусом (не выпущен / выпускается / выпущен / ошибка); пометка «Testnet».
- Убрать бейдж «Mainnet» в шапке (`CollectionPage`, `ArtworkDetailPage`): он вводит в заблуждение.

### API

| Эндпоинт | Назначение |
| --- | --- |
| `POST /wallet/proof-payload` | Выдаёт одноразовый payload для `ton_proof` |
| `POST /wallet/link` | Проверяет подпись `ton_proof` и привязывает адрес к пользователю; запускает выпуск ожидающих паспортов |
| `DELETE /wallet/link` | Отвязывает кошелёк (уже выпущенные NFT остаются на нём) |
| `GET /metadata/:spiritId.json` | Метаданные TEP-64 |
| `POST /artworks/:id/chain-sync` | Админ: сверить владельца и статус с блокчейном |

### Данные (Prisma)

- `User.walletAddress` — уникальный, необязательный.
- `Artwork.passportAddress`, `Artwork.mintTxHash`, `Artwork.chainStatus`: `NOT_MINTED` → `AWAITING_WALLET` → `MINTING` → `MINTED` или `FAILED`. Это четвёртый независимый статус рядом со статусом работы, верификации и владением.
- Новое событие provenance `PASSPORT_MINTED`. Привязка кошелька — событие пользователя, а не работы, поэтому в provenance не пишется.

### Поток выпуска

1. Админ одобряет верификацию (как сейчас).
2. Если у владельца нет привязанного кошелька — `chainStatus = AWAITING_WALLET`, выпуск произойдёт после привязки.
3. Иначе бэкенд строит метаданные, считает хэши и отправляет `mint_passport` с сервисного кошелька Spirit (`MINTING`).
4. Фоновая проверка через get-методы подтверждает контракт → `MINTED`, записывает адрес и событие `PASSPORT_MINTED`. Таймаут или отказ → `FAILED` с возможностью повтора из админки.

### Синхронизация владельца

Прямая передача разрешена, поэтому NFT может сменить владельца вне приложения. Источник истины для владельца выпущенного паспорта — блокчейн. Периодическая задача и `chain-sync` читают `owner_address`. Если адрес привязан к другому пользователю, они меняют `currentOwnerId` и пишут `OWNERSHIP_TRANSFERRED`. Если не привязан — помечают «владелец вне Spirit».

### Конфигурация

`BLOCKCHAIN_MODE=real`, `TON_NETWORK=testnet`, `TON_API_ENDPOINT` и `TON_API_KEY` (toncenter или TonAPI), `SPIRIT_REGISTRY_ADDRESS`, `TON_SERVICE_WALLET_MNEMONIC` — только в секретах Railway, никогда в репозитории. Перед включением перевести `TELEGRAM_AUTH_MODE` в `strict` и сменить пароль админа по умолчанию: с реальным кошельком режим `dev` позволит выдать себя за другого пользователя.

## Блок C. Автотесты

Сейчас в репозитории нет ни одного теста, хотя `CLAUDE.md` требует их для бизнес-логики. Релиз добавляет три уровня тестов и запуск в CI (GitHub Actions) на каждый PR.

### 1. Контракты (локальный эмулятор блокчейна, без сети)

На каждое правило — минимум один позитивный и один негативный тест:

1. Verifier выпускает паспорт; адрес совпадает с `get_nft_address_by_index`, владелец и поля корректны.
2. Не-verifier не может выпустить паспорт и изменить верификацию.
3. Второй паспорт с тем же `chip_uid_hash` отклоняется.
4. Паспорт отклоняет служебные сообщения не от реестра, в том числе от владельца.
5. `update_metadata` и `rebind_chip` переводят APPROVED в PENDING.
6. Владелец передаёт паспорт напрямую; чужой адрес передать не может.
7. Каждое изменение увеличивает `event_count` и обновляет `last_event_hash` по формуле.
8. Authority добавляет и удаляет verifier; удалённый больше ничего не может.
9. Get-методы совместимы со стандартом (`get_nft_data`, `get_collection_data`, `royalty_params`).
10. В контрактах хватает баланса на хранение, лишние TON возвращаются отправителю.
11. Контракт продажи (блок D), первичная продажа: при цене P Spirit получает P × 1200 / 10000, художник P × 800 / 10000, продавец остаток; NFT у покупателя — всё в одной транзакции.
12. Перепродажа: доли 200 / 200, продавец получает остаток.
13. Округление: при цене, которая не делится нацело, сумма трёх выплат равна цене, остаток у продавца.
14. Оплата меньше цены отклоняется и возвращается целиком, NFT остаётся на контракте; переплата возвращается покупателю.
15. Контракт принимает NFT только от своего паспорта и только от продавца; до прихода NFT купить нельзя.
16. Продавец отменяет листинг и получает NFT обратно; чужой адрес отменить не может; после продажи отмена и повторная покупка невозможны.
17. Доли и адреса получателей нельзя изменить после развёртывания; сумма долей не больше 10000.

### 2. Бизнес-логика бэкенда (Vitest уже есть в `apps/api/package.json`, тестовая Postgres)

- Верификация: переходы статусов, запрет повторной верификации, права (только владелец или админ).
- Покупка: смена владельца атомарна, нельзя купить свою работу, нельзя подтвердить чужую транзакцию.
- Листинг: работа с выпущенным паспортом выставляется только через контракт продажи, мок-покупка для неё отклоняется. Первичная продажа или перепродажа определяется верно; без кошелька художника листинг отклоняется.
- Покупка через контракт: смена владельца, `SOLD` у листинга и `COMPLETED` у транзакции происходят только после подтверждения в блокчейне; повторная обработка того же события ничего не дублирует; сообщение фронтенда об оплате ничего не меняет.
- Provenance: события пишутся в правильном порядке и не меняются.
- Выпуск: переходы `chainStatus`, ожидание кошелька, повтор после `FAILED` — с моком `BlockchainService`.
- `ton_proof`: чужая подпись, просроченный или повторно использованный payload отклоняются; один кошелёк нельзя привязать к двум пользователям.
- Стартовая коллекция выдаётся ровно один раз при одновременных входах. Сейчас это баг: при проверке PR #2 новый пользователь получил 6 работ вместо 3.

### 3. Интеграционный тест в testnet (вручную или по кнопке, не на каждый PR)

Один скрипт проходит весь путь на настоящей сети: выпуск паспорта → чтение через API → передача на другой кошелёк → синхронизация владельца → выставление на продажу → покупка с третьего кошелька → проверка выплат продавцу, художнику и Spirit.

## Блок D. Продажа через контракт

Работу с выпущенным паспортом продают через контракт продажи на Tolk. Схема та же, что у маркетплейсов TON: на каждый листинг разворачивается отдельный контракт, владелец передаёт ему NFT, покупатель платит, и контракт одной транзакцией отдаёт NFT покупателю и делит деньги. Пока NFT лежит на контракте продажи, распорядиться им может только этот контракт, поэтому поле блокировки в паспорте не нужно.

### Комиссии

| Продажа | Spirit | Художник | Продавец | Пример с ценой 1000 TON |
| --- | --- | --- | --- | --- |
| Первичная | 12% | 8% | 80% | 120 · 80 · 800 |
| Перепродажа | 2% | 2% | 96% | 20 · 20 · 960 |

- Доли хранятся в базисных пунктах (1200 / 800 и 200 / 200), остаток от округления получает продавец.
- Первичная продажа или перепродажа, решает бэкенд: первичная, если у работы ещё нет ни одной завершённой продажи (ни через мок, ни через контракт). Доли и адреса бэкенд передаёт в параметрах при развёртывании контракта, потом они не меняются.
- Если первую продажу ведёт сам художник, он получает две выплаты, 80% и 8%, то есть 88% (допущение, ждёт подтверждения).
- Комиссию сети (газ) платит покупатель сверх цены, выплаты продавцу из-за неё не уменьшаются.
- Сделки вне Spirit (Getgems, прямая передача) комиссий не дают: TEP-66 только сообщает условия маркетплейсу.

### Контракт продажи (`SpiritSale`)

| Хранилище | Назначение |
| --- | --- |
| `nft_address`, `registry_address` | Паспорт, который продаётся, и реестр Spirit |
| `seller_address` | Владелец, выставивший работу |
| `price` | Цена в nanoTON, фиксируется при выставлении |
| `spirit_address`, `spirit_bps` | Кошелёк Spirit и его доля |
| `artist_address`, `artist_bps` | Кошелёк художника и его доля |
| `state` | Ожидает NFT → активен → продан или отменён |

| Операция | Кто вызывает | Что делает |
| --- | --- | --- |
| приём NFT (`ownership_assigned`) | паспорт | Принимает NFT только от `nft_address` и только от продавца; переводит в «активен» |
| `buy` | любой | Если сумма не меньше цены и запаса на газ: отдаёт NFT покупателю, отправляет три выплаты, сдачу возвращает. Иначе возвращает всю сумму |
| `cancel` | продавец или authority | Возвращает NFT продавцу; после продажи невозможна |

Get-метод `get_sale_data` отдаёт все поля и состояние. Контракт разворачивает сервисный кошелёк Spirit, и бэкенд признаёт только контракты, адрес которых сам вычислил из кода и параметров: чужой контракт с нулевыми комиссиями для Spirit — просто внешняя сделка.

### Поток продажи

1. Владелец нажимает «Продать» и указывает цену в TON. Бэкенд проверяет права и статусы, определяет тип продажи, разворачивает контракт и создаёт `Listing` в новом статусе `PENDING`.
2. Mini App через TON Connect просит владельца подписать передачу NFT на адрес контракта. Когда фоновая проверка видит NFT на контракте, листинг становится `ACTIVE` и появляется в каталоге.
3. Покупатель с привязанным кошельком нажимает «Купить» и подписывает перевод на контракт через TON Connect. Бэкенд создаёт `Transaction` в статусе `PENDING`.
4. Фоновая проверка видит, что контракт продан и NFT у покупателя: бэкенд меняет `currentOwnerId`, ставит листингу `SOLD`, транзакции `COMPLETED` с хэшем, пишет в provenance `SOLD` и `OWNERSHIP_TRANSFERRED`. Об успехе решает только бэкенд по данным блокчейна, не фронтенд.
5. Отмена: владелец подписывает `cancel`, NFT возвращается, листинг `CANCELLED`, событие `LISTING_CANCELLED`.

### Изменения в данных и API

- `ListingStatus`: новый статус `PENDING` (ждём NFT на контракте).
- `Listing.saleContractAddress`, `Listing.saleKind` (`PRIMARY` / `RESALE`), `Listing.spiritBps`, `Listing.artistBps`. Цена такого листинга хранится в TON (`currency = TON`), а не в долларах.
- `Transaction.blockchainRef` (поле уже есть) — хэш транзакции покупки.
- Существующие `POST /listings` и `POST /purchases` для работ с паспортом возвращают данные для TON Connect (адрес контракта, сумму, payload) вместо мок-оплаты. `POST /purchases/confirm` для таких работ не меняет владельца: это делает только фоновая проверка.
- Мок `PaymentService` остаётся для демо-работ без паспорта.

## Testnet

Да, testnet нужен, и весь этот релиз работает только в нём. Testnet — отдельная сеть TON с бесплатными тестовыми монетами: контракты ведут себя так же, как в основной сети, но ошибка ничего не стоит.

Зачем он нужен именно Spirit:

- Опубликованный в блокчейне контракт нельзя просто исправить. Ошибка в mainnet означает новый контракт и перенос всех паспортов.
- Команда впервые работает с TON, и testnet — безопасное место учиться.
- Демо для инвесторов можно показывать в testnet: паспорт настоящий и виден в Tonviewer, но честно помечен как тестовый.
- Перед mainnet нужен внешний аудит контрактов, а аудиторы проверяют код, уже отработавший в testnet.

Как развернуть:

1. Создать сервисный кошелёк Spirit для testnet и получить тестовые TON из официального бота-крана (testnet faucet).
2. Развернуть реестр скриптом из `packages/contracts`, записать адрес в `SPIRIT_REGISTRY_ADDRESS`.
3. Добавить сервисный кошелёк в verifier.
4. Включить на Railway `BLOCKCHAIN_MODE=real` и `TON_NETWORK=testnet`.
5. В Tonkeeper включить testnet-режим и подключить кошелёк в Mini App.

Переход на mainnet — отдельное решение после аудита; в этот релиз он не входит.
